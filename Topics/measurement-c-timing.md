<a id="why-this-matters"></a>
## 1. Why this matters

A timing prediction is an engineering claim.

A measurement is evidence about that claim.

Good embedded-system work keeps those roles separate:

```text
predict -> measure -> compare -> explain
```

The same principle applies whether timing is generated by handwritten assembly or by C source compiled into machine instructions.

Exact processor timing belongs to the instructions that actually execute, not to the number of source-code lines.

## 2. What you should be able to do

After working through this guide, you should be able to:

- choose an oscilloscope or frequency counter based on the measurement question;

- identify common limitations of timing measurements;

- explain why C source statements do not map one-to-one to PIC instructions;
- use compiler output/disassembly to reason about exact compiled-code timing;
- distinguish what simulation can verify from what requires hardware measurement.

<a id="core-model"></a>
## 4. Core model and vocabulary

<a id="measurement-strategy"></a>
### Match the instrument to the question

Use an **oscilloscope** when you need to see time-domain behavior such as:

- pulse width;
- duty cycle;
- rise/fall behavior;
- edge relationships;
- transient behavior;
- jitter/variation;
- sequence relationships.

Use a **frequency counter** when the primary question is a stable repetitive frequency and high resolution/precision over many cycles is useful.

Neither instrument is universally “better.”

<a id="prediction-evidence"></a>
### Prediction and evidence are different

Before measuring, record:

- expected pulse width;
- expected period;
- expected frequency;
- relevant tolerance;
- exact code path or hardware mechanism used for the prediction.

Then measure the same quantity.

Do not silently change the formula after seeing the instrument result.

<a id="how-it-works"></a>
## 5. How it works

<a id="oscilloscope"></a>
### Oscilloscope measurements

For a pulse waveform, the scope can directly show:

- edge placement;
- HIGH and LOW time;
- full period;
- rise/fall shape;
- overshoot/ringing;
- relationships between channels.

**Official visual reference:** Tektronix's [How to Use an Oscilloscope and Probe](https://www.tek.com/vn/documents/primer/setting-and-using-oscilloscope) includes time/frequency examples and Figure 69 for pulse width/rise-time measurement.

Focus on the defined measurement points. Instrument timing numbers only make sense when the measurement boundary is clear.

<a id="frequency-counter"></a>
### Frequency-counter measurements

A frequency counter is well suited to stable repetitive signals.

Modern counters may use direct counting, reciprocal techniques, or both depending on instrument/function.

**Official reference:** Keysight's [Frequency Counter overview](https://www.keysight.com/il/en/products/rf-power-meters/frequency-counters.html) explains direct and reciprocal frequency measurement.

A counter reading still depends on:

- trigger/input conditions;
- signal quality;
- reference timebase;
- gate/measurement method;
- instrument specifications.

<a id="measurement-limitations"></a>
### Measurement limitations matter

Possible limitations include:

- oscilloscope sample rate and time resolution;
- time-base accuracy;
- counter timebase accuracy;
- trigger stability;
- probe attenuation/compensation;
- measuring too few cycles;
- rounded display values;
- oscillator tolerance/drift;
- loading from the measurement setup.

A screenshot without scale, trigger, probe, and signal context is weak evidence.

<a id="compiled-c"></a>
### C source does not determine exact cycle timing

Consider:

```c
for (int i = 0; i < n; i++)
{
    ;
}
```

The exact PIC cycle count depends on the generated machine code.

Important variables include:

- compiler version;
- optimization settings;
- selected target;
- integer width;
- register allocation;
- surrounding code;
- generated branch structure;
- inlining or other optimization.

The correct exact-timing workflow is:

```text
C source -> compile -> inspect generated instructions -> trace actual path -> count cycles
```

<a id="simulation-hardware"></a>
### Simulation and hardware answer different questions

Simulator/disassembly can help verify:

- generated instructions;
- Program Counter path;
- register state;
- branch behavior;
- instruction-cycle counts.

Hardware measurement is still needed for:

- actual oscillator frequency;
- physical output edges;
- loading;
- probe effects;
- analog behavior;
- real external events.

<a id="worked-examples"></a>
## 6. Worked examples

<a id="twice-frequency-example"></a>
### Worked example: measured frequency is twice the prediction

**Observation**

```text
predicted = 500 Hz
measured  = 1 kHz
```

**First question**

Was a half-cycle mistaken for the full waveform period?

If software delays 500 us between toggles:

```text
half-cycle = 500 us
full period = 1000 us
frequency = 1 kHz
```

The measurement can be correct while the original interpretation was wrong.

<a id="c-timing-example"></a>
### Worked example: one C loop, several possible instruction paths

Suppose two compiler builds use the same C source but different optimization settings.

One build may keep a counter in RAM and execute extra load/store instructions.

Another may keep state in a register or optimize part of the loop away.

The source text did not change, but the executed instruction path did.

**Meaning**

Do not assign an exact cycle count to C source until the generated target instructions are inspected.

<a id="apply-verify-troubleshoot"></a>
## 7. Apply, verify, and troubleshoot

<a id="disagreement-workflow"></a>
### When prediction and measurement disagree

Use this order:

```text
Is FOSC actually what was assumed?
-> Is the intended build/source actually programmed?
-> Was the executed path counted correctly?
-> Was pulse width confused with full period?
-> Are compiler/generated instructions what you assumed?
-> Are instrument/probe/time-base settings correct?
-> Only then investigate subtler device/hardware effects.
```

Do not start by inventing a correction factor.

<a id="measurement-record"></a>
### Record enough evidence to reproduce the claim

A useful timing record includes:

- predicted value;
- formula/path used;
- instrument;
- probe/input setup;
- timebase or counter mode;
- measured value;
- tolerance/uncertainty that matters;
- explanation of disagreement if present.

The goal is not a pretty screenshot. The goal is evidence another person can interpret.

<a id="answer-key"></a>
## 9. Answer key

1. Oscilloscope.
2. Frequency counter.
3. Check whether a pulse width/half-cycle was mistaken for the full period.
4. The compiler generates machine instructions, and the instruction path depends on compiler/target/optimization details.
5. Inspect the generated assembly/disassembly and trace the actual path.
6. Verify clock, build, path, waveform interpretation, and instrument setup first.
7. Examples: sample/time resolution, timebase accuracy, triggering, probe setup, input loading, gate/mode, oscillator tolerance.
8. Simulator can establish instruction/control/register behavior and generated code path without physical analog uncertainty.
9. The scope can show actual physical waveform timing, edge shape, loading effects, oscillator reality, and probe-visible behavior.

## 10. What you should be able to explain without notes

You should be able to:

- choose an instrument based on the quantity being measured;
- record a falsifiable timing prediction;
- distinguish half-cycle, period, and frequency;

- explain why exact C timing requires generated machine code;
- separate simulator evidence from hardware evidence.
